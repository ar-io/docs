## Quick lookup

| Symptom | What to check |
| --- | --- |
| Release number is old or ends in `-pre` | Upgrade from the `main` branch. |
| Gateway shows as offline on https://gateways.ar.io | Check that `https://<your-gateway>/ar-io/healthcheck` answers. |
| `/ar-io/observer/reports/current` says "Report pending" | Nothing. Wait for the report. |
| Observing your gateway shows failures | `AR_IO_WALLET`, `ARNS_ROOT_HOST`, wildcard DNS and certificates, and `/chunk/<offset>`. |
| Failed offset (chunk-proof) checks | Upgrade core to Release 85 or later. See [Failed offset (chunk-proof) checks](#failed-offset-chunk-proof-checks). |
| `.env` changes have no effect | Restart the gateway with `docker compose`. |
| Out of disk space, but the disk has free space | Inode exhaustion (`df -i`). |
| ArNS names don't load | `ARNS_ROOT_HOST` in `.env`, and the wildcard DNS record. |
| "Your connection is not private" | Renew your SSL certificates. |
| 404 page from NGINX | NGINX configuration, and whether the gateway is running. |
| 502 from NGINX | The gateway's logs. |
| certbot can't issue certificates | Wait for the DNS TXT records to propagate. |

## General troubleshooting

<Accordions>
<Accordion title="My release number is old, or ends in -pre">

Your release number is the `release` field of `https://<your-gateway>/ar-io/info`. If it is lower than the current release, [upgrade your gateway](/build/run-a-gateway/manage/upgrading-a-gateway).

A release ending in `-pre`, such as `89-pre`, means your gateway runs the `develop` branch. That branch holds unreleased work and is less stable than `main`. Switch to `main` from your gateway's directory:

```console
sudo docker compose down --rmi all
git checkout main
git pull
sudo docker compose up -d
```

If the old images stay in use, remove every unused Docker image and start again:

```console
sudo docker compose down
sudo docker system prune -a
sudo docker compose up -d
```

`docker system prune -a` also removes stopped containers, unused networks and the images of any other Docker project on the machine.

</Accordion>

<Accordion title="My gateway shows as offline on https://gateways.ar.io">

The Network Portal checks a gateway by requesting `https://<your-gateway>/ar-io/healthcheck` from your browser. That request can fail while the gateway works, for example when your own network blocks it. Check the gateway from another machine:

```console
curl https://<your-gateway>/ar-io/healthcheck
```

If it answers, your gateway is up and the portal will show it as online again.

</Accordion>

<Accordion title="/ar-io/observer/reports/current says 'Report pending'">

This is normal. The observer answers `{"message":"Report pending"}` until it has a report for the current epoch.

</Accordion>

<Accordion title="Observing my gateway shows failures">

An observation of a gateway passes only if all three of its checks pass:

- **Ownership.** The `wallet` your gateway reports at `/ar-io/info` must match the wallet the gateway joined the network with. It comes from `AR_IO_WALLET` in `.env`. If it is wrong, fix it and restart the gateway.
- **ArNS.** At least 80% of the ArNS names checked must resolve to the same data as on the observer's reference gateway. If they fail, check that `ARNS_ROOT_HOST` is set in `.env`, and that you have a wildcard DNS record and certificate for `*.<your-gateway>`.
- **Offsets (chunk proofs).** Your gateway must serve `/chunk/<offset>` with a Merkle proof that validates against the chain. See [Failed offset (chunk-proof) checks](#failed-offset-chunk-proof-checks).

[Troubleshooting failed epochs](#troubleshooting-failed-epochs) explains how observers count these checks across an epoch.

</Accordion>

<Accordion title="I changed .env, but nothing changed on my gateway">

The gateway reads `.env` only when its containers start. Restart it from your gateway's directory:

```console
sudo docker compose down
sudo docker compose up -d
```

</Accordion>

<Accordion title="I get an out of disk space error, but the disk has free space">

The filesystem has probably run out of inodes, so it can't create new files even with space free. Check:

```console
df -i
```

If a line shows `IUse%` at 100%, free inodes by deleting files from the gateway's cache directories, `data/chunks` and `data/contiguous`. The gateway fetches deleted cache data again when it needs it. Don't delete `data/sqlite`: it holds your gateway's index.

</Accordion>

<Accordion title="My gateway won't resolve ArNS names">

1. Check that `ARNS_ROOT_HOST` is set in `.env` to your gateway's domain, for example `ARNS_ROOT_HOST=turbo-gateway.com`, then restart the gateway.
2. Check your DNS. ArNS names are served on subdomains, so you need a wildcard record (`*.<your-domain>`) pointing at your gateway, and a certificate that covers it. Set it up the same way as the record for your main domain.

</Accordion>

<Accordion title="My browser shows 'Your connection is not private'">

Your SSL certificates have expired. Expired certificates are the most common reason a working gateway suddenly stops. Renew them with the certbot command you used to set up your gateway:

```console
sudo certbot certonly --manual --preferred-challenges dns -d <your-domain>.com -d '*.<your-domain>.com'
```

certbot certificates expire after 90 days, so you have to rerun this command each time unless you set up [automatic renewal](/build/run-a-gateway/manage/ssl-certs). After renewing, restart NGINX, which keeps serving the old certificates until it restarts:

```console
sudo service nginx restart
```

</Accordion>

<Accordion title="My domain shows a 404 page from NGINX">

A 404 page from NGINX means your domain points at the right machine, but NGINX isn't forwarding requests to the gateway. Either NGINX is misconfigured or the gateway isn't running.

Follow the networking steps in the [production setup](/build/run-a-gateway/quick-start#production-setup-with-custom-domain) to check your NGINX configuration. Restarting NGINX makes it drop an old configuration it is still holding:

```console
sudo service nginx restart
```

</Accordion>

<Accordion title="My domain shows a 502 error from NGINX">

A 502 means NGINX is working, but it got an error, or no answer, from your gateway when it forwarded the request. Check that the gateway is running (`sudo docker compose ps`) and read its logs (`sudo docker compose logs core`).

</Accordion>

<Accordion title="certbot can't generate my SSL certificates">

With the manual DNS challenge from the setup guide, wait for your TXT records to propagate before you continue. Check propagation with a tool such as [dnschecker.org](https://dnschecker.org). If it still fails, see the [certbot instructions](https://certbot.eff.org/instructions).

</Accordion>

<Accordion title="My logs show errors, but everything works">

Gateways recover from most temporary errors without affecting service. Investigate only if an error repeats or the gateway stops working.

</Accordion>

<Accordion title="I was selected as an observer, but my logs say no report was submitted">

- Each observer picks a window covering half the epoch, checks every gateway during it, and submits one report after the window closes. Until then there is nothing to submit.
- The observer submits only in epochs where it is a prescribed observer. In other epochs it logs that it is not prescribed and skips the submission.
- Your observer wallet must be the one registered for your gateway. Check it on your gateway's page at https://gateways.ar.io.

</Accordion>

<Accordion title="My logs changed from importing blocks to 'Polling for block'">

This is normal. Your gateway has caught up with the newest Arweave block and is waiting for the next one.

</Accordion>

<Accordion title="My logs show 'Error resolving name with resolver'">

This is normal when it happens now and then. Your gateway first resolves an ArNS name itself, from the chain. If that takes more than 3 seconds (`ARNS_COMPOSITE_RESOLVER_TIMEOUT_MS`), it asks a trusted gateway instead (`TRUSTED_ARNS_GATEWAY_URL`, turbo-gateway.com by default).

</Accordion>

<Accordion title="My gateway failed an epoch">

Work through these checks in order:

1. Open your gateway in a browser and check that its certificate is valid.
2. Load an ArNS name on your gateway. If it fails, read the browser console and your gateway's logs.
3. Read the reports of the observers that failed your gateway. Each one lists the reason. See [Accessing the observer report](#accessing-the-observer-report).
4. If the reports show failed offset checks, see [Failed offset (chunk-proof) checks](#failed-offset-chunk-proof-checks).

</Accordion>
</Accordions>

## Troubleshooting failed epochs

### Overview

Every gateway on the network runs an [observer](/learn/oip). In each epoch, up to 50 gateways are prescribed as observers. Each prescribed observer checks every gateway and submits one report, which records whether each gateway passed and why it failed.

Each observer checks each gateway 3 times in an epoch (`OBSERVATIONS_PER_GATEWAY`), at moments spread over a window covering half the epoch. Its report marks a gateway as failed if fewer than 2 of those observations pass (`MAJORITY_VOTE_THRESHOLD`). One observation passes when:

- the ownership check passes,
- at least 80% of the ArNS names checked pass, and
- the offset check passes.

A gateway fails the epoch when more than half of the observers that submitted a report mark it as failed. A gateway that fails an epoch gets no gateway reward for it. If it was also a prescribed observer and submitted its report, it still gets its observer reward.

To diagnose a failure, first try to load data from the gateway in a browser. If that doesn't show the problem, read the observer reports.

### Manual observation

You can run an observation of any gateway at any time from the [Network Portal](https://gateways.ar.io):

1. Open the [Network Portal](https://gateways.ar.io).
2. Select the gateway from the list of gateways.
3. Click **Observe**, at the right of the gateway's header, next to **Reports**.

![Gateway header in the Network Portal, with the Observe link highlighted to the right of Reports](/content/portal-observe-button.png)

4. Check the **ArNS names** field, at the right of the Observe header. It holds the current epoch's prescribed names. You can change them or add more, separated by commas.
5. Click **Run Observation**, next to the field.

![Observe page with two prescribed ArNS names in the ArNS names field and the Run Observation button highlighted, above an empty Reports table](/content/portal-run-observation.png)

The results open in the **Observation Details** panel on the right. The observation also appears in the table below the header, saved in your browser, where you can click it to open it again.

![Observation Details panel for turbo-gateway.com, with the gateway, Ownership and ArNS Assessment all Passed, and status code, ID and data hash passing for each of two ArNS names](/content/portal-observation-details.png)

A manual observation runs the ownership and ArNS checks from your browser, once. It doesn't run the offset check, and it isn't a majority of 3, so it can pass where an observer's report failed.

### Accessing the observer report

To read the reports that failed a gateway, use the [Network Portal](https://gateways.ar.io):

1. Open the [Network Portal](https://gateways.ar.io).
2. Select the gateway from the list of gateways.
3. In the **Observations of this gateway** panel, select the epoch from the dropdown on the right. The panel lists the observers that failed the gateway in that epoch. Click **Read why** to list each observer's reasons in the panel.
4. To open an observer's full report, click the **View Report** button to the right of that observer's address.

![Observations of this gateway panel showing Failed by 1 of 17 observers for the current epoch, with the View Report button beside the observer address highlighted](/content/portal-view-report.png)

5. In the report, find your gateway in the **Observed Host** column and click its row. The **Observation Details** panel opens with that gateway's results.

### Understanding the observer report

For each ArNS name checked, the report shows what the observer expected, what your gateway returned, and a failure reason if the check failed. The failure reason is the error message the observer got, or the list of fields that didn't match. Below are the most common reasons and how to fix them.

#### Timeout awaiting 'socket', or Timeout awaiting 'connect'

```text
Timeout awaiting 'socket' for 7000ms
```

```text
Timeout awaiting 'connect' for 5000ms
```

The observer couldn't get an answer from your gateway in time. It allows 5 seconds for the DNS lookup, 5 seconds to connect, 2 seconds for the TLS handshake (`secureConnect`), and 7 seconds of silence on an open connection (`socket`).

Many causes have nothing to do with your gateway. A few of these failures among many passing checks are not a problem.

If most or all names fail this way, the observer can't reach your gateway at all. Check by:

- opening your gateway in a browser,
- running a [manual observation](#manual-observation), and
- using `curl` or `ping` from another network.

If those fail too:

- Check Docker and the gateway's logs to see if the gateway is running.
- Check that the SSL certificates are valid for your gateway's domain.
- Check your domain's DNS records. Wrong or conflicting records cause connection problems.

Some operators running gateways on home networks have found their internet provider blocking, throttling or delaying traffic to the gateway. If nothing above helps, ask your provider.

[Grafana](/build/extensions/grafana) shows your gateway's ArNS resolution times. If they stay high, make sure the gateway runs the latest release.

#### Cert has expired

```text
certificate has expired
```

Your gateway's SSL certificate has expired. Renew it, point your reverse proxy (NGINX or another) at the new certificate, and restart the proxy.

#### dataHashDigest mismatch

```text
dataHashDigest mismatch
```

Your gateway answered, but the hash of the data it returned differs from the hash of the observer's reference copy. The reason can list other fields that differed too, for example `contentType mismatch, dataHashDigest mismatch`. Causes:

- **Your gateway cached a JSON wrapper instead of the data (before Release 88).** arweave.net, one of the default trusted gateways, answers some requests with a JSON document describing the data instead of the data itself. Before Release 88, a gateway that fetched from it could cache that wrapper and serve it as the item, with the wrong hash and content type. Release 88 fixes the fetch, but copies cached before the upgrade keep being served until you purge them. See [Purging cached JSON wrappers](#purging-cached-json-wrappers).
- **The gateway returned cached data that is older than the current data on the network.** This happens occasionally and resolves itself.
- **The gateway runs on testnet or devnet.** Gateways joined to the ar.io network must run on mainnet to pass observation. If most or all names fail with this reason, check this first.
- **The gateway returns fraudulent data on purpose.** This takes rewriting the gateway's code, and catching it is a main purpose of the Observation and Incentive Protocol.

The bundled observer uses your own gateway (`ARNS_ROOT_HOST`) as its reference, or turbo-gateway.com and ar-io.net when `ARNS_ROOT_HOST` isn't set. It doesn't use a gateway as its own reference while another reference can answer.

##### Purging cached JSON wrappers

A wrapped copy starts with `{"accept-ranges"`. Take the ID from the report (the resolved ID of the failing name), and check what your gateway serves for it:

```console
curl -s https://<your-gateway>/<id> | head -c 32; echo
```

If the output starts with `{"accept-ranges"`, make your gateway forget its record of that ID, so the next request fetches the data again. This needs Release 88 and your `ADMIN_API_KEY`:

```console
curl -X POST 'http://localhost:3000/ar-io/admin/invalidate-data' \
  -H 'Authorization: Bearer <ADMIN_API_KEY>' \
  -H 'Content-Type: application/json' \
  -d '{"id": "<id>"}'
```

The answer is `{"id":"<id>","removed":true}`, or `"removed":false` if the gateway had no record of the ID. This doesn't reach caches in front of the gateway. If you run an NGINX cache or a CDN, purge the ID there too, for example with the [cache bypass header](/build/run-a-gateway/manage/nginx-caching#cache-bypass-header).

#### Response code 502 (Bad Gateway)

```text
Response code 502 (Bad Gateway)
```

The observer reached your server, but your reverse proxy answered 502. This is almost always a reverse proxy problem. Check that the proxy is running and forwards requests to the gateway.

On NGINX, test the configuration with `sudo nginx -t`. If it has no errors, reload NGINX with `sudo nginx -s reload`.

The gateway itself may also be stopped. Check Docker and the gateway's logs.

#### Response code 503 (Service Unavailable)

```text
Response code 503 (Service Unavailable)
```

The observer reached your server, but the reverse proxy couldn't get an answer from the gateway behind it. The cause is usually temporary: the gateway is overloaded or restarting. One or two of these in a report are not a problem. If every name in the report fails this way, the gateway has probably crashed. Restart it.

#### connect EHOSTUNREACH

```text
connect EHOSTUNREACH <gateway-ip>:443
```

The observer found no network route to your gateway's IP address. This is almost always a DNS or network problem. Check that your domain's DNS records point at the right IP address, and that your firewall and router let connections in on port 443. Your reverse proxy's logs may show more.

#### getaddrinfo ENOTFOUND

```text
getaddrinfo ENOTFOUND <arns-name>.<gateway-domain>
```

The observer couldn't find a DNS record for the name. Your gateway probably has no valid DNS record for its domain, or for the wildcard subdomain ArNS names need. One or two of these in a report can be a temporary problem with the observer's DNS server. If every name in the report fails this way, your DNS records are missing or wrong.

#### Hostname/IP does not match certificate's altnames: Host: \<gateway-domain\>. is not in the cert's altnames: DNS:\<gateway-domain\>

```text
Hostname/IP does not match certificate's altnames: Host: <arns-name>.<gateway-domain>. is not in the cert's altnames: DNS:<gateway-domain>
```

Your gateway's SSL certificate doesn't cover the name the observer requested. In the example, the certificate covers only the gateway's domain, not the wildcard `*.<gateway-domain>` that ArNS names are served on. The same error appears when a gateway changes domain and keeps the old certificate. Get a certificate that covers both the domain and its wildcard, point your reverse proxy at it, and restart the proxy.

#### write EPROTO \<connection-id\>:error:\<error-code\>:SSL routines:ssl3_read_bytes:tlsv1 unrecognized name:\<path-to-openssl-source\>:SSL alert number 112

```text
write EPROTO <connection-id>:error:0A000458:SSL routines:ssl3_read_bytes:tlsv1 unrecognized name:<path-to-openssl-source>:SSL alert number 112
```

Your server has no certificate or server block for the name the observer requested. This almost always means the gateway has no certificate set up for its wildcard subdomain. Get a certificate that covers the wildcard, point your reverse proxy at it, and restart the proxy.

### Failed offset (chunk-proof) checks

From Release 85, observers check that gateways serve chunks. By default every gateway is checked in every epoch (`OFFSET_OBSERVATION_SAMPLE_RATE`, `1.0`). An observer that sets a lower rate checks a share of gateways, the same share as every other observer at that rate.

A checked gateway must serve `/chunk/<offset>` with a Merkle proof that validates against the chain. The observer tries up to 4 offsets (`OFFSET_SAMPLE_COUNT`) and stops at the first that validates, so a gateway fails only when every offset fails. Timeouts, error statuses and bad proofs all count as failures.

By default a failed offset check fails the observation (`OFFSET_OBSERVATION_ENFORCEMENT_ENABLED=true`), like a failed ownership or ArNS check, and the 2-of-3 majority still applies. If the observer couldn't judge the check because its own lookups failed, it records the check as `inconclusive`, which never fails a gateway.

The report lists the samples of the observer's best observation of your gateway under `offsetAssessments`. Each failed sample names its offset and a `failureCategory`:

| `failureCategory` | Meaning |
| --- | --- |
| `timeout` | The gateway didn't answer `/chunk/<offset>` in time. |
| `network` | The connection failed: DNS, refused, TLS or reset. |
| `http_status` | The gateway answered with an error status. A `404` means it couldn't serve the chunk. |
| `invalid_chunk` | The response wasn't a usable chunk: not JSON, an empty or oversized chunk, or a missing or unreadable `data_path`. |
| `bad_proof` | The `data_path` Merkle proof doesn't validate against the chain. |
| `unverifiable` | The gateway served a chunk, but the observer couldn't check it against the chain because its own lookups failed. It never counts as a pass. A check is `inconclusive` only when all its samples are `unverifiable`. |

To fix it:

- **Upgrade core to Release 85 or later.** Release 85 fixed chunk fetches that answered `404` for chunks the network holds. A gateway now asks the preferred Arweave nodes first, in the order that serves it best from where it runs, and tries up to 8 peers per chunk instead of 5 (`ARWEAVE_PEER_CHUNK_GET_MAX_PEER_ATTEMPT_COUNT`).
- **Test the offset yourself**, with an offset from the report:

  ```bash
  curl -s -o /dev/null -w '%{http_code}\n' https://<your-gateway>/chunk/<offset>
  ```

  `200` means your gateway served the chunk. `404` means no source it tried had the chunk. From Release 88, `503` means it couldn't fetch the chunk in time.
- **Allow for warm-up.** After each restart, a gateway needs about 100 chunk requests to learn which preferred nodes serve it well. Until then, chunk fetches fail more often.
- **Check your own node lists.** If you set `PREFERRED_CHUNK_GET_NODE_URLS` or `PREFERRED_CHUNK_POST_NODE_URLS`, remove `tip-5.arweave.xyz`. Release 85 dropped it from the defaults because it stopped answering.

## FAQ

<Accordions>
<Accordion title="Why was my reward different this epoch?">

- Each epoch pays out a share of the protocol balance: 0.1% at first, falling linearly between epochs 365 and 547 to 0.05%, where it stays. 90% of that goes to gateways and 10% to observers. Each gateway's share depends on the protocol balance and the number of gateways, so it changes when either changes.
- A gateway that fails an epoch gets no gateway reward for it.
- Observer rewards are separate. If your gateway is a prescribed observer in an epoch and submits its report, it gets an observer reward on top.

</Accordion>

<Accordion title="I have a high stake on my gateway. Why am I not an observer?">

Observers are drawn at random, weighted by more than stake:

- **Stake weight**: your total stake, including delegated stake, relative to the network minimum.
- **Tenure weight**: how long your gateway has been on the network. It grows with tenure and stops at 4, after 2 years.
- **Gateway performance ratio weight**: the share of epochs your gateway passed.
- **Observer performance ratio weight**: the share of your observer epochs in which you submitted a report.

The composite weight is the product of the four: stake × tenure × gateway performance × observer performance.

Up to 50 gateways are chosen as observers each epoch. With more than 50 gateways on the network, the draw uses these weights, so tenure and performance affect your chances as much as stake does.

</Accordion>

<Accordion title="I withdrew my stake, but received less than I withdrew">

Withdrawing delegated stake, or operator stake above the minimum, starts a 30-day lock. You can skip the lock for a fee, which starts at 50% of the amount and falls over the lock period to 10%. If you withdrew without waiting, you paid that fee. The minimum operator stake is returned through the separate network leave process.

</Accordion>

<Accordion title="Why can't I withdraw my stake?">

The minimum operator stake (20,000 ARIO) can't be withdrawn while the gateway is on the network. It is returned only through the network leave process, and it is lost if the gateway is removed from the network for failing too many epochs in a row.

</Accordion>

<Accordion title="How do I move my gateway to a new server?">

1. If you can, leave the old server running while you set up the new one.
2. Set up the new server the same way as the old one, including its SSL certificates.
3. Use the same gateway wallet on the new server. Keep the same observer wallet too: you can change it, but that takes extra steps.
4. Point your DNS A records at the new server.
5. When the records have propagated and the new gateway works, shut down the old server.

You don't need to change anything in the network contract or on https://gateways.ar.io.

</Accordion>

<Accordion title="Can I change my gateway's domain?">

Yes:

1. Point the new domain at your gateway and get SSL certificates for it, including the wildcard.
2. Add the new domain to NGINX (or your reverse proxy) and restart it.
3. Set `ARNS_ROOT_HOST` in `.env` to the new domain and restart the gateway.
4. On https://gateways.ar.io, update your gateway's settings with the new domain.

</Accordion>
</Accordions>
