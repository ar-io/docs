## Overview

A new gateway builds its index of the Arweave network block by block. That can take days or weeks, depending on your hardware and on how much data you index. You can skip most of it in one of two ways:

- [Import a SQLite snapshot](#import-a-sqlite-snapshot). The 2025-04-23 snapshot holds transactions and the data items uploaded through ArDrive products, including Turbo, up to block 1645229.
- [Bootstrap from L1 bands](#bootstrap-from-l1-bands) (Release 85 or later). Your gateway follows the chain tip and, while it runs, fills in the Arweave base layer beneath it (blocks, transactions, tags and owners) from signed bands that another gateway publishes. Data items are not included.

<Callout type="info">
  Looking to resolve data items faster without a full database? [Index
  Sharing](/build/run-a-gateway/manage/index-sharing) lets your gateway
  subscribe to another gateway's root transaction indexes, about 21 GB today
  and kept current, instead of importing a snapshot.
</Callout>

<Callout type="info" title="Note">
The below instructions are designed to be used in a linux environment. Windows and MacOS users must modify the instructions to use the appropriate package manager/ command syntax for their platform.

Unless otherwise specified, all commands should be run from the root directory of the gateway.

</Callout>

## Import a SQLite Snapshot

SQLite snapshots are large and hard to update in steps, so ar.io distributes them over BitTorrent.

<Callout type="warning" title="IMPORTANT">
  Importing a snapshot deletes your existing database and replaces it with the
  snapshot.
</Callout>

<Steps>
<Step>
### Install a Torrent Client

Any BitTorrent client works. For example, [transmission-cli](https://github.com/transmission/transmission):

```bash
# Ubuntu/Debian
sudo apt-get install transmission-cli

# CentOS/RHEL
sudo yum install transmission-cli

# macOS
brew install transmission-cli
```

</Step>

<Step>
### Download the Snapshot

```bash
transmission-cli "magnet:?xt=urn:btih:62ca6e05248e6df59fac9e38252e9c71951294ed&dn=2025-04-23-sqlite.tar.gz&tr=udp%3A%2F%2Ftracker.opentrackr.org%3A1337%2Fannounce&tr=http%3A%2F%2Ftracker.opentrackr.org%3A1337%2Fannounce&tr=udp%3A%2F%2Fopen.demonii.com%3A1337%2Fannounce&tr=udp%3A%2F%2Ftracker.torrent.eu.org%3A451%2Fannounce&tr=udp%3A%2F%2Fp4p.arenabg.com%3A1337%2Fannounce&tr=https%3A%2F%2Ftracker.bt4g.com%3A443%2Fannounce"
```

This downloads `2025-04-23-sqlite.tar.gz`, about 42.8 GB. Check that it arrived whole with `ls -lh 2025-04-23-sqlite.tar.gz`.

Seeding the torrent after the download is not required, but it keeps the snapshot available for other operators.

</Step>

<Step>
### Extract the Archive

```bash
tar -xzf 2025-04-23-sqlite.tar.gz
ls -la 2025-04-23-sqlite/
```

This creates a directory named after the file, without `.tar.gz`, that holds the SQLite database files. If you use a different snapshot, replace the file name.

</Step>

<Step>
### Stop the Gateway

```bash
docker compose down
```

If you start your gateway with your own `-f` files, pass the same ones to every `docker compose` command on this page.

</Step>

<Step>
### Replace the Database

Back up your existing database (optional), then move the snapshot into `data/sqlite`:

```bash
mkdir sqlite-backup
mv data/sqlite/* sqlite-backup/
mv 2025-04-23-sqlite/* data/sqlite/
```

If you skip the backup, delete the old files with `rm data/sqlite/*` before the last command.

</Step>

<Step>
### Start the Gateway

```bash
docker compose up -d
```

</Step>

<Step>
### Verify the Import

Watch the gateway logs for the block height being imported:

```bash
docker compose logs -f core
```

The 2025-04-23 snapshot was taken at block `1645229`. If the import worked, the gateway imports blocks from 1645230 upward. The [Grafana extension](/build/extensions/grafana) also shows the last block imported.

</Step>
</Steps>

## Bootstrap from L1 Bands

<Callout type="info">
  **Release Requirement**: L1 bands, and the `ar-io-node` CLI that imports
  them, arrive in gateway Release 85, which is not released yet. Your gateway
  and the publisher you subscribe to must both run it.
</Callout>

An L1 band (`parquet-l1`) holds the Arweave base layer for a range of block heights, as Parquet files: blocks, transactions, tags and owners. Gateways that publish them sign every file, and your gateway checks each one before it installs the band. Your gateway then fills its `core.db` from the installed bands, instead of indexing the chain from block 0.

L1 bands carry no data items. Your gateway still unbundles the bundles your filters select, and it does that for imported history only if you also set `BACKFILL_BUNDLE_RECORDS`.

There are two ways to do it:

- Fill the history while the gateway runs, as below. This is the usual way. It works on a new gateway, on one that began mid-chain, and on one with a hole in what it holds.
- [Import with the gateway stopped](#import-l1-bands-with-the-gateway-stopped). Faster, but only for a new `core.db` that the gateway has never run on.

With `L1_BAND_IMPORT_ENABLED=true`, core runs `ar-io-node index-l1-import --fill` every 10 minutes (`L1_BAND_IMPORT_INTERVAL_SECONDS`, counted from the end of the last run), as a child process, so a crash in the import can't take the gateway down. A fill writes only the heights `core.db` lacks beneath what the block importer writes itself, so nothing your gateway indexed is rewritten. It writes in short transactions with a pause after each, so the gateway keeps indexing and serving the whole time.

On a new gateway, set this up **before the first start** and leave `START_HEIGHT` unset. With an empty `core.db`, the block importer then starts at the chain tip instead of block 0, and the history beneath it arrives as the bands do.

### Prerequisites

- A gateway on Release 85 or later
- Room on disk: about 15 GB for the bands, and about 120 GB for a `core.db` that covers the whole chain. The setup script sets the Index Sharing disk budget to 100 GiB if it is unset, and warns if yours is lower

<Steps>
<Step>
### Subscribe with `--l1`

L1 bands arrive through [Index Sharing](/build/run-a-gateway/manage/index-sharing). Run the setup script with `--l1`, first with `--dry-run` to see the changes:

```bash
./tools/index-swarm-setup --subscribe 34LYvMptiDvBP5sqfh1oAd6Q4qFsy4PWaZ1HTFmML7h5 --l1 --torrent --dry-run
./tools/index-swarm-setup --subscribe 34LYvMptiDvBP5sqfh1oAd6Q4qFsy4PWaZ1HTFmML7h5 --l1 --torrent --restart
```

`--l1` subscribes to the publisher's L1 bands as well as its root-TX bands, sets `L1_BAND_IMPORT_ENABLED=true`, and restarts core. Leave out `--torrent` to move bands over HTTP only.

</Step>

<Step>
### Check It

```bash
./tools/index-swarm-status
```

Bands install under `data/indexes/installed/parquet-l1`, and each fill writes what they hold. On the gateway's `/ar-io/__gateway_metrics`, `l1_band_import_runs_total{result}` counts fills (`filled`, `idle` or `failed`), `l1_band_import_rows_total` the rows written, and `l1_band_import_uncovered_heights` the heights no installed band holds yet.

</Step>
</Steps>

Uncovered heights are normal for a while: bands still downloading, and, on a new gateway, the heights between the newest band and where it began, which the publisher's next tip band holds, usually within a day. A run with nothing to fill writes nothing. Only one import or fill runs against a `core.db` at a time.

## Import L1 Bands with the Gateway Stopped

The fastest way to load the whole chain into an empty database, at the cost of the gateway being down while it runs. It is only for a **new** `core.db` that the gateway has not run on yet. The import refuses a `core.db` that another process is writing to, and one that holds unstable blocks (the `new_*` tables). A gateway that has run always holds some, because it moves blocks to the stable tables only once they are 18 deep. For a gateway that already runs, [fill while it runs](#bootstrap-from-l1-bands) instead.

### Prerequisites

- A gateway on Release 85 or later, and a migrated `core.db` (`yarn db:migrate up`; the core service also runs it when it starts). The import refuses one without its ledger table
- Room on disk: about 15 GB for the bands, and about 120 GB for a `core.db` that covers the whole chain. The import refuses to start without the space it needs
- Time: the whole chain takes about 15 hours on 12 cores. The import logs its progress once a minute

<Steps>
<Step>
### Subscribe to L1 Bands

A subscription takes L1 bands only when it names them, so add `parquet-l1` to the `name` list in `INDEX_SWARM_SUBSCRIBE`:

```bash
INDEX_SWARM_SUBSCRIBE='[{"publisher":"34LYvMptiDvBP5sqfh1oAd6Q4qFsy4PWaZ1HTFmML7h5","name":["root-tx-index","parquet-l1"]}]'
```

Then recreate the `index-swarm` sidecar and wait until `./tools/index-swarm-status` shows the bands installed under `data/indexes/installed/parquet-l1`.

</Step>

<Step>
### Stop the Gateway

Stop only the core service, with the same `-f` files your gateway was started with:

```bash
docker compose stop core
```

</Step>

<Step>
### Import the Bands

Run it from the gateway's directory. The tool runs in the core image, so the host needs only Docker:

```bash
./tools/ar-io-node index-l1-import \
  --bands-dir data/indexes/installed/parquet-l1 \
  --core-db data/sqlite/core.db \
  --cache-mib 8192
```

Bands import in height order, lowest first. `--cache-mib` sets SQLite's page cache for the run (default 1024 MiB); give it what your machine can spare, since a larger cache keeps a long import fast. An interrupted run is safe: run the command again and it carries on from the last band that landed. `--max-bands` splits the work across several runs.

</Step>

<Step>
### Start the Gateway

```bash
docker compose up -d --no-deps core
```

The block importer continues from the highest height imported.

</Step>
</Steps>

To check a set of bands, or your gateway's own `core.db`, against the chain, use `./tools/ar-io-node index-l1-verify`. Every option, and the JSON each command prints, is in the [`ar-io-node` CLI reference](https://github.com/ar-io/ar-io-node/blob/develop/docs/cli.md#index-l1-import).
